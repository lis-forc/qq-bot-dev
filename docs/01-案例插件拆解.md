# 案例插件拆解 · astrbot_plugin_qq 与 astrbot_plugin_sign

> 目的：从两份真实插件里提炼「AstrBot v4 + OneBot v11（aiocqhttp）」的实战写法，
> 并对照官方文档找出**做得对的**、**可以简化的**、**有风险的**。
> 目标形态：只跑 OneBot v11（NapCat），不用 qq_official。

---

## 一、两个样本的定位

| | `astrbot_plugin_qq`（九寰） | `astrbot_plugin_sign` |
|---|---|---|
| 规模 | main.py 933 行 + core 1500 行 + utils 253 行 | 4 个文件共 ~250 行 |
| 风格 | 分层工程化：入口 / 服务 / 数据库 / 工具 | 单文件式，main.py 一个类搞定 |
| 命令注册 | **不用** `@filter.command`，单入口 + 手写路由 | 用 `@filter.command("签到")` |
| 配置 | `_conf_schema.json` + `JiuHuanConfig` 强类型封装 | **没有** `_conf_schema.json` |
| 存储 | SQLite，放 `data/plugin_data/<插件名>/`（✅ 规范） | SQLite，放 `data/plugins_db/`（❌ 自己造的目录） |
| 元数据 | `metadata.yaml`（含 `astrbot_version`、`support_platforms`） | `metadata.yaml` + `@register(...)` **双写** |
| 多输出 | 纯文本 | PIL 生成签到图 |

两个都是 `metadata.yaml` 为准，`@register` 只是兼容旧版（文档明说优先级低于 metadata.yaml）。

## 三、核心手法：单入口 + 手工路由（本项目的关键决策）

### 3.1 为什么不用 `@filter.command`

`@filter.command("签到")` 的问题是：
1. **必须有唤醒前缀**（默认 `/`），用户打「签到」不触发，得打 `/签到`。
2. 一条消息只能命中一个指令，多个中文口令要写一堆装饰器。
3. `/help` 里会列出所有指令，混在系统指令里。

九寰的做法是**只注册一个 ALL 监听器**，自己在里面剥文本、比对口令。所以用户直接打「立名 李明 男」就行，不需要 `/`：

```python
@filter.event_message_type(filter.EventMessageType.ALL)
async def on_event(self, event: AstrMessageEvent):
    if event.get_platform_name() not in PLATFORMS:      # 平台白名单
        return
    raw = event.message_obj.raw_message if event.message_obj else None
    group_id = _event_group_id(event, raw)
    if not group_id or not self.config.is_group_enabled(group_id):   # 群白名单
        return

    data_group_id = self.config.resolve_data_group_id(group_id)      # 多群互通→主群
    if data_group_id not in self.initialized_groups:
        self.sects.ensure_defaults(data_group_id)                    # 懒初始化
        self.initialized_groups.add(data_group_id)

    increase = self._parse_group_increase(raw)      # ① 入群通知
    if increase:
        async for r in self._handle_group_increase(...): yield r
        return

    card_changed = self._parse_group_card_change(raw)   # ② 群名片被改
    if card_changed:
        await self.profiles.enforce_member_card(...)
        return

    sender_id = str(event.get_sender_id() or _raw_get(raw, "user_id") or "")
    if not sender_id or sender_id == str(event.get_self_id()):   # ③ 屏蔽自己
        return

    text = event.message_str or ""
    if not text:
        return
    if self.db.get_member(data_group_id, sender_id):
        await self.profiles.enforce_member_card(event, data_group_id, sender_id, actual_group_id)  # ④ 自动纠正名片

    handled = False
    async for r in self._handle_command(event, data_group_id, actual_group_id, sender_id, text):  # ⑤ 口语令
        handled = True
        yield r
    if handled:
        event.stop_event()                    # ★ 关键：阻止 LLM 再回复一遍
        if not self.config.count_command_messages:
            return

    async for r in self._handle_regular_message(...):   # ⑥ 普通发言：计数、发寰玉、自动签到
        yield r
```

**`event.stop_event()` 这一行的意义**：证实了「插件回复后要不要拦 LLM」这个我之前标为待验证的点 —— 答案是**要主动 stop**，否则 AI 还会再回一遍。

### 3.2 路由的三件套工具函数（可直接复用）

```python
def _compact(text: str) -> str:
    return re.sub(r"\s+", " ", text or "").strip()

def _strip_at_text(text: str) -> str:
    """把 @张三(12345) / @12345 这类残留从参数里剥掉"""
    text = re.sub(r"@[\.\(]*\d+[\)]*", "", text)
    text = re.sub(r"@\S+", "", text)
    text = re.sub(r"[\u4e00-\u9fff\w]*\(\d+\)", "", text)
    return _compact(text.replace("@", ""))

def _drop_prefix(text: str, prefixes: tuple[str, ...]) -> str | None:
    """命中前缀返回剩余参数，未命中返回 None —— 路由的核心判断式"""
    cleaned = _compact(text)
    for prefix in prefixes:
        if cleaned == prefix:                    # 只有口令、没有参数
            return ""
        if cleaned.startswith(prefix + " "):
            return _compact(cleaned[len(prefix):])
    return None
```

用法模式统一成：

```python
args = _drop_prefix(text, ("立名", "入籍", "登记"))
if args is not None and args:
    ...; return
if text in {"立名", "入籍", "登记"}:          # 无参数 → 只回格式提示
    yield event.plain_result("立名格式：立名 李明 男"); return
```

`_drop_prefix` 返回 `""` vs `None` 的区分很关键：`None` = 没命中，`""` = 命中了但没给参数。

其它小工具：`_parse_int_arg`（抠第一个数字当页码）、`_parse_duration_seconds`（`10分钟`→600 秒，封顶 2592000）。

## 四、穿透 OneBot 原生接口（utils/helpers.py 是重点参考）

### 4.1 调协议端 API 的统一姿势

```python
await event.bot.api.call_action("set_group_ban",
    group_id=int(actual_group_id), user_id=int(user_id), duration=600)
```

九寰用到的 action：

| 场景 | action | 参数 |
|---|---|---|
| 拿群成员列表 | `get_group_member_list` | `group_id` |
| 拿单个成员信息（判角色） | `get_group_member_info` | `group_id`, `user_id` |
| 改群名片 | `set_group_card` | `group_id`, `user_id`, `card` |
| 踢人 | `set_group_kick` | `group_id`, `user_id`, `reject_add_request` |
| 禁言/解禁 | `set_group_ban` | `group_id`, `user_id`, `duration`（0=解禁，上限 30 天） |
| 全群禁言 | `set_group_whole_ban` | `group_id`, `enable` |

统一的写法是：**包一层，返回 bool，失败只记日志不抛**。

```python
async def mute_user(event, user_id, duration, group_id=None) -> bool:
    actual = group_id or event.get_group_id()
    if not actual: return False
    duration = max(0, min(duration, 2_592_000))     # 30 天上限，NapCat 会拒绝更长的
    try:
        await event.bot.api.call_action("set_group_ban",
            group_id=int(actual), user_id=int(user_id), duration=duration)
        return True
    except Exception as exc:
        logger.error(f"禁言成员失败: {exc}", exc_info=True)
        return False
```

注意：`call_action` 返回的东西形态不固定（有时 `{"data": [...]}`，有时直接 list），helpers 里做了双重判断兜底。这个防御是必要的。

### 4.2 判断"机器人自己有没有管理员权限"

```python
async def is_bot_admin(event, group_id) -> bool:
    bot_id = event.get_self_id() or event.message_obj.self_id
    member = await get_group_member_info(event, group_id, bot_id)
    return member.get("role") in {"owner", "admin"}
```

**所有群管动作前都先查这个**，否则会拿到一个含糊的失败。九寰在每个群管命令里都写了这一句，值得照抄。

### 4.3 @ 目标提取（`get_at_targets`）：五级兜底

这是我认为最值得抄的一个函数。提取"用户 @ 了谁"要面对五种数据形态：

1. AstrBot 消息链里的 `Comp.At`
2. 消息链里 type 字段是 `"at"` 的组件
3. `raw_message.message` 里的 OneBot 段数组（`{"type":"at","data":{"qq":...}}`）
4. `raw.mentions`（qq_official 的形态）
5. 全都没有 → 从纯文本 `@12345` 正则抠；再不行就 `@昵称` 去 `get_group_member_list` 里模糊匹配

只跑 OneBot v11 的话第 1、2、3、5 就够，第 4 路（mentions）可以删。

## 五、配置层：`JiuHuanConfig` 的封装法

不直接用 dict，而是包一层带默认值和类型收敛的 property：

```python
@property
def message_reward_step(self) -> int:
    return max(1, int(self.raw.get("message_reward_step", 100) or 100))

@property
def currency_transfer_received(self) -> int:
    cost = self.currency_transfer_cost
    received = max(1, int(self.raw.get("currency_transfer_received", 8) or 8))
    return min(cost, received)          # 到账不能超过扣除，防止刷玉
```

三个细节值得学：
- 每个 property 都有**兜底默认值**，配置项缺失/被删不会崩。
- 用 `max()/min()` 做**值域收敛**，`0` 也不会被当成"没配置"（`or 100` 之后仍走 max）。
- 跨字段约束放在 property 里（到账 ≤ 扣除）。

`_conf_schema.json` 里两个 `template_list` 用得不错：

- `default_sects`：模板项 `sect`，`display_item: "name"` —— WebUI 折叠列表显示宗门名。
- `linked_group_sets`：模板项 `group_set`，`name` + `group_ids`(list) —— 多群互通分组。

`items` 里嵌套 `list` 是允许的（`group_ids` 就是 `type: "list"`）。

## 六、权限体系：四级 + 双来源取高

```python
async def get_level(self, event, group_id, actual_group_id, user_id) -> int:
    member = self.db.get_member(group_id, user_id)
    manual_level = member.get("permission_level") if member else None
    owner_id, admin_ids = await get_group_owner_and_admins(event, actual_group_id)
    mapped = 1
    if owner_id and str(user_id) == str(owner_id):
        mapped = self.config.owner_default_level       # 群主 4 级
    elif str(user_id) in {...admin_ids}:
        mapped = self.config.admin_default_level       # 管理员 3 级
    return max(mapped, min(4, max(1, int(manual_level or 0))))  # 取高，防误降
```

- 权限有两个来源：**QQ 群角色映射** 和 **插件内手动授阶**，取较高者。
- 每个受限命令开头一行 `ok, _ = await self.permissions.require(..., 3)`，不通过就回一句"XX需三级权限"，模式非常统一。
- 帮助文本按 level 动态拼（`_render_help(level)`），低等级看不到高等级口令。

> 代价：`get_level` 每次都要 `get_group_member_list`（拉全群成员）。群大 + 命令频繁时这是个坑，建议按群缓存 30~60 秒。

## 七、数据层

- 连接：`sqlite3.connect(path, check_same_thread=False)` + `row_factory = sqlite3.Row`
- 表：`members`(复合主键 group_id+user_id) / `sects` / `sect_elder_members` / `message_daily_stats` / `currency_logs` / `red_packets` / `red_packet_claims` / `relationships` / `operation_logs`
- **所有表都带 `group_id`**，天然支持多群隔间；配合 `resolve_data_group_id` 实现多群互通（写到主群 ID）。
- 迁移函数 `_migrate_db`：`PRAGMA table_info(members)` 查列，缺了就 `ALTER TABLE ADD COLUMN` —— 轻量、可重复执行，适合插件迭代。
- 每次改钱/改权限都写 `operation_logs`，可审计。

## 八、两个样本暴露出的问题（要不要改，你定）

### 8.1 性能与稳定性

1. **每条消息 2 次协议端 API 调用。**
   `on_event` 里，只要是小号里已立名成员发消息，就 `enforce_member_card()` → `get_group_member_info()` + `set_group_card()`，而且**不判断名片是否已经正确**，每次都硬写一遍。
   大群一天几千条消息 = 几千次 WS 请求，容易触发 NapCat/QQ 的频率限制。
   → 建议：先查 QQ 名片，与期望值不同才 `set_group_card`；再按群缓存成员角色。

2. **SQLite 同步调用跑在 async 处理器里。**
   `self.db.xxx()` 全部是阻塞 IO。群活跃时会在事件循环里排队。
   → 建议：`await asyncio.to_thread(self.db.xxx, ...)`，或换 `aiosqlite`。

3. **未注册成员的刷屏风险。**（这条比较要紧）
   `_handle_regular_message` 开头：非成员就 `yield event.plain_result("请先完成立名…")`。
   而它是在"没命中任何口令"时**每条消息**都会执行的分支 —— 也就是一个没立名的人随便发 10 句话，机器人回 10 条。
   → 建议：加冷却（同一人 5 分钟最多提醒一次，用 dict 或 KV 存时间戳）。

### 8.2 规范对齐

4. `__init__(self, context: Context, config: dict)` —— 建议写 `config: AstrBotConfig`，语义更准（它是 dict 子类，改了不影响运行）。
5. **缺 `requirements.txt`**。`astrbot_plugin_qq` 纯标准库所以没事，但 `astrbot_plugin_sign` 用了 `PIL`，插件目录里却没有 `requirements.txt`，换台机器装会 `ModuleNotFoundError`。
6. `astrbot_plugin_sign` 把库放在 `data/plugins_db/`（自己用 `dirname(dirname(plugin_dir))` 拼出来的），不符合文档规定的 `data/plugin_data/<插件名>/`，且路径推导很脆。九寰的写法是对的。
7. `astrbot_plugin_sign` 的临时图固定叫 `temp_sign.png`，两人同时签到会串图；且 `yield` 后才删文件。建议 `tempfile.mkstemp()` 或用文件名带 user_id。
8. `astrbot_plugin_sign` 用 `sqlite3.connect(...)` 默认 `check_same_thread=True`，在 AstrBot 的异步环境里多线程访问有隐患；九寰设了 `False`。
9. 九寰跨类调了私有方法 `self.db._today()`，建议提成公开方法。

### 8.3 可简化（因为我们只用 OneBot v11）

10. `PLATFORMS = {"aiocqhttp", "qqofficial", "qq_official"}` → 只留 `"aiocqhttp"`。
11. `_raw_get` 里对 `event/data/raw_data/raw_message/raw` 五层嵌套的探测，是为兼容 qq_official 的；OneBot v11 下 `raw_message` 就是平铺 dict，可以直接 `raw.get(key)`。
12. `get_at_targets` 的 `mentions` 分支（第 4 路）可以删。
13. `metadata.yaml` 的 `support_platforms` 只留 `aiocqhttp`。

### 8.4 待实测确认

14. **`group_increase` / `group_card` 通知到底能不能到插件？**
    九寰是从 `event.message_obj.raw_message` 里读 `post_type == "notice"` 来判断的。这说明作者是按"notice 也能进 on_event"来写的。但 AstrBot 的 aiocqhttp 适配器是否把所有 notice 都封装成事件下发给插件，**每个版本差异很大**。
    → 验证方法：在 `on_event` 最前面临时 `logger.info(f"RAW: {raw}")`，拉人进群一次，看日志里有没有这条。

## 九、如果现在从零写一个插件，骨架长这样

```
astrbot_plugin_xxx/
├── metadata.yaml          # name/desc/version/author/repo + support_platforms:[aiocqhttp] + astrbot_version
├── main.py                # class Xxx(Star)；__init__ 串 db/config/services；terminate 关连接
├── _conf_schema.json      # 只放用户真的要调的项，全部给 default
├── requirements.txt       # 有第三方依赖就必须有
├── core/
│   ├── config.py          # 强类型 property + 兜底 + 值域收敛
│   ├── database.py        # sqlite3(check_same_thread=False) + 迁移 + 带 group_id
│   └── services.py        # 业务逻辑，纯函数式，不碰 event
├── utils/
│   ├── router.py          # _compact / _strip_at_text / _drop_prefix / _parse_int_arg
│   └── onebot.py          # call_action 封装：mute/kick/set_card/whole_ban/is_bot_admin
├── images/                # 静态资源
└── README.md
```

事件入口的固定套路：

```
平台过滤 → 群白名单 → 群间数据映射 → notice 分支 → 屏蔽自己 → 口令路由
   → 命中: yield 结果 + event.stop_event()
   → 未命中: 普通消息逻辑（计数/签到，注意加冷却）
```
